## 拆分原则

- 每票包含自己的数据保存、应用行为、用户入口／实际流程入口及对应测试，不分成“先数据库、再 API、再 UI”的水平层。
- 01 的范围只建立最小可保存任务，不同时塞入状态历史、用户清单、Today、Calendar 或 Agent 接线。
- 03 不依赖 02：归档保留已有状态即可独立成立，不要求状态编辑 UI 先完成。02 与 03 在相同数据边界协作时须协调共享代码；文件冲突不是硬依赖。
- 05 不依赖 04：两者复用 01–03 的操作，Calendar 无需等待 Today 页面改造。最终 09 验证它们整合后一致。
- 07 不依赖 04/05：外部入口的前提是完整任务／状态／清单行为，Tasks 本身已能显示其结果。08 在 07 的契约上完成真实流程，而非只交兼容输入样例。
- 09 的依赖经传递覆盖全部九票；可以按 01→09 顺序执行，但不是每票都依赖上一票。
- 01／06 无前置。每个新执行任务必须使用已包含其前置成果的 checkout；不能因 worktree 从旧默认分支开始而丢失依赖。
- 暂无证据需要独立宽泛重构票。若复用现有 Today 应用边界需要提取少量 Task 操作，在 01 开头做保持行为的必要整理，然后交付完整新增／重读切片。不复活旧 Exercise runtime，不直接搬入 throwaway 原型实现。
- 4.1 Habit 管理、提醒／重复任务／子任务等不混入本轮。
